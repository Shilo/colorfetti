## Mechanism supported by current source

The second focus receipt is now retained and independently recalculated: `preview-focus-1792321019726.json`,20rows,0errors,all focus/removal flags true,two exact PNGs with the same baseline/candidate hash. Its paired latency/CPU values agree with the numbers above. This closes the missing-repeat-link bookkeeping item; it does not remove the repeated small CPU adverse observation or turn close-event timing into full input-to-visible latency.

`App.svelte` stores the initiating wall DOM element in plain `viewTrigger` in `openImage`. The normal viewer close handler captures that element, clears `viewing`, awaits a Svelte tick, then focuses or blurs the captured trigger. It never clears the persistent `viewTrigger` slot. Removing the image later detaches that wall button.

The frozen baseline bundle installs a delegated handler on that button. Its `W(event, node, handler)` function writes into `node[Br]`; the Tile click callback reaches the component props and its item. The corresponding installed Svelte source is `src/internal/client/dom/elements/events.js`: `delegated` stores handlers on `element[event_symbol]`. `destroy_effect` in `reactivity/effects.js` removes DOM and clears effect references, but does not clear these node properties. A retained detached button can therefore keep the Tile closure and immutable item reachable even after the wall's keyed component is destroyed. Exactly which component locals V8 retains is an empirical heap question; this is not a claim that every detached node retains every local.

The frozen runtime also clears Svelte's `last_propagated_event` in a later timer task. A plateau surviving11seconds and forced GC is not explained by an indefinitely retained last event in this version. Preserve that distinction rather than attributing the application slot to Svelte globally.

Other potential persistent roots are `sharedTrigger` and `paletteTrigger`. `shared` is already cleared when its item leaves `items`, but the plain trigger is not; opening the editor from Preview can store a viewer Save button. These paths need their own capture/removal receipts before claiming the same retained size or bundling broader fixes. Bound `clearTrigger` has different framework-owned cleanup, while the persistent More button remains connected normally.

`viewing` itself stores a whole item even though the `viewed` derived value uses only its ID. Normal close clears it. Source deletion while Preview is mounted could instead make `viewed` null, removing the component without its native close callback and leaving that item in `viewing`; this is a separate lifecycle hypothesis, not yet a reproduced user-flow bug. It must not be silently included in the normal-close diagnosis.

## Falsifiers and measurement controls

1. Compare an imported48-frame256² clip removed without ever opening Preview against the identical clip opened/closed in Preview before removal. Match count/export readiness and the same post-remove URL delay, two GC passes and observation window.
2. Separate Preview-only from Preview+Save; otherwise export work/URL or asynchronous encoding ownership could explain the difference. Last URL delay must exceed the existing10seconds. A ready-URL count reaching zero does not alone prove all source refs dropped.
3. After the problematic removal, open/close a tiny source's Preview. If replacing `viewTrigger` retires the large backing plateau, that supports the slot mechanism without changing application source. If not, investigate shared/editor roots and the actual retained graph before editing.
4. A candidate that changes only close-time slot cleanup should reduce retained source/backing bytes after removal without changing imported pixels, Preview controls, focus/blur return, hidden-wall pause/resume, count queues or native output bytes. GC samples are finite retained backing observations, not a precise global peak-memory bound or a speedup.

## Narrow correction boundary if proven

Capture `trigger` and keyboard intent locally at close entry, clear `viewTrigger` and keyboard state before `await tick()`, then perform the existing focus/blur operation on the captured local. The transient local remains until focus completes; the app slot must not outlive that need. Clearing before awaiting also avoids a late old callback clearing a newly opened viewer's trigger. Do not mutate framework event symbols or detached-node handlers as a workaround.

For a separately demonstrated sheet/editor case, preserve `previewShared`'s local trigger captured before `sheet.close()`, and preserve the editor's connected-trigger/Palette-button focus fallback. Clearing the shared slot must not break the sheet→Preview handoff. Source evidence warrants targeted experiments; it does not warrant a blanket DOM-reference cleanup patch without lifecycle proof.

## Fresh primary guidance

Consulted October18: Chrome's [memory investigation guidance](https://developer.chrome.com/docs/devtools/memory-problems/) recommends examining detached DOM retained by JavaScript and releasing references after their purpose ends. Its [heap snapshot guidance](https://developer.chrome.com/docs/devtools/memory-problems/heap-snapshots) distinguishes reachable objects, closure contexts and retainer comparisons. Applied here: inspect only the owned test page, avoid creating a new console/global reference to the large source, compare post-reversal states after GC, and separate sampled JavaScript/backing sizes from OS memory. These support the proposed experiment; they do not establish that Colorfetti leaks or quantify its retained bytes without new receipts. Neither guide justifies a new WeakRef compatibility dependency or a framework event-property mutation.
